## 3.2 Scalability evaluation
| Layer | Scaling behaviour | Limit to mention |
|---|---|---|
| CloudFront / S3 | Effectively unlimited reads | - |
| API Gateway HTTP API | Auto; throttle configurable | Default account limit 10,000 rps (we cap at 100) |
| Lambda | One execution environment per concurrent request | Account concurrency quota (default 1,000, may be lower on new accounts) |
| DynamoDB on-demand | Auto-scales read/write | Hot partition risk: `Notices` uses one partition key -> fine for reads of 50 items, would need sharding at very high write rates |
| Cognito | Managed | Sign-in API rate quotas |

Evidence to cite: Lambda *ConcurrentExecutions* graph rising during the test, zero DynamoDB throttles, flat p95.

## 3.4 Technical justification (design decisions)
| Decision | Justification | Trade-off |
|---|---|---|
| Serverless over EC2 | Bursty workload, zero idle cost, no patching | Cold starts; vendor lock-in |
| DynamoDB over RDS | Access patterns are key-based; auto-scales; no connections to manage from Lambda | No ad-hoc joins/reports (use Athena/export if analytics needed) |
| HTTP API over REST API | ~70% cheaper, lower latency, native JWT authorizer | Fewer features (no usage plans/API keys) |
| Presigned S3 uploads | File bytes never pass through Lambda -> cheaper, faster, no 6 MB payload limit | Needs CORS config |
| Rules + Comprehend hybrid tagging | Deterministic, free baseline; AI only to escalate priority; system keeps working if AI fails | Rules need maintenance; English only |
| Stream-driven notifications | Decouples API latency from e-mail sending | Eventual (seconds) delivery |
| Infrastructure as Code | Repeatable, reviewable, one-command teardown | Learning curve |
